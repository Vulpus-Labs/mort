# ADR 0009: The `mort` command line

- **Status:** Accepted
- **Date:** 2026-11-18

## Context

The agent and the person both drive mort from a shell. Output must be
short enough to read in an agent's context, and exact enough to act on.
Many tasks are sequences of calls that should share a view of project
state.

## Decision

1. **Subcommands mirror the RPC groups:**
   - `mort status`
   - `mort tracks` and `mort track add | rm | set`
   - `mort fx` and `mort fx add | rm | bypass | preset`
   - `mort params` and `mort set`
   - `mort automate`
   - `mort midi`
   - `mort play` and `mort render`
   - `mort measure`, `mort map`, `mort findings`, `mort compare`
   - `mort summary`, `mort report` and `mort frames` (ADR 0007 §4)
   - `mort thresholds`, `mort thresholds set KEY VALUE` and `mort
     thresholds reset KEY` (ADR 0012 §7)
   - `mort view [--port N] [--open]`, which serves the map view until
     stopped (ADR 0012 §9)
   - `mort undo` and `mort redo`
   - `mort install`
   - `mort call <method> <json>`, an escape hatch for any RPC.
2. **Output:** compact aligned text by default, made for reading. Each
   command prints the project `state` it saw on its last line. `--json`
   prints the RPC result as it is.
3. **Names in, ids out:** commands accept track and FX names and musical
   positions (ADR 0003). Printed output gives names, with ids in
   `--json`.
4. **Scripts:** `mort run file.kdl` (or `-` for stdin) runs a sequence of
   commands as one `batch` where they are edits, carrying `expect_state`
   through. A failed step stops the script and reports the step and the
   error.
   - Each KDL node is one command line. The node's name and arguments
     are its words; a property `key=value` becomes `--key value`;
     `key=#true` becomes `--key`, and `#false` leaves it out. Every step
     is parsed before any runs.
   - Edits in a row are held and sent as one batch, labelled with the
     file name or `--summary`. It gets one undo point and is checked
     against the state the first held edit read.
   - Reads run at once. `tracks.list` shows the tracks and FX the held
     edits add, with placeholder ids that the bridge fills in from
     earlier results (ADR 0002 §7). So `fx add` then `set` on the new FX
     works in one batch; `set` names the parameter, which the bridge
     looks up when the batch runs.
   - Steps that need the edits made (`measure`, `play`, `render`,
     `stop`, `undo`, `redo`) send the batch first, then expect the state
     it left. A `commit` node sends it too.
   - `status`, `call`, `install` and `run` are not steps.
5. **Waiting:** commands that start jobs wait for them by default and
   print progress to stderr. `--no-wait` prints the job id.
6. **Exit codes:**
   - 0: success
   - 1: error from the bridge (its `kind` is printed)
   - 2: usage error
   - 3: no bridge running

## Consequences

- An agent's loop is plain shell: `mort measure --stale`, then
  `mort findings`, then an edit, then `mort compare`.
- `mort call` keeps every RPC reachable before the CLI has a command for
  it.
